# ffsim/gpu: the GPU proxy (route 2)

Equal-step CUDA runs of the **unmodified** submission `train.py`, driven by a virtual Trainium
charged clock so that every clock-keyed switch (k1 -> k2 -> k4 accumulation phases, the eight MTP
stages, cooldown start, EMA save level, stop) fires at the same step number as on chip C, and the run
ends at the same step count (K60: 2,361 steps, 492,175,360 tokens; `configs/schedule-K60-TT1793.json`). The GPU answers one question,
"does this change reach a lower val_bpb after the same optimizer trajectory?", and is trusted only
for the recipe families in which it has reproduced Trainium pairs. Protocol, numbers and the
arithmetic behind them: `ffsim/gpu/PROTOCOL.md`.

**Status (release, Oct 2026): the proxy ran.** On 30 Sep 2026 it ran on single-L40S g6e boxes. Its first four
equal-step runs reproduced chip C: K60 seed 73 scored 0.959952 on the GPU vs 0.959948 on Trainium, the
attention-source effect came out -0.00187 vs -0.00181, and LeakyReLU(0.35)^2 vs relu^2 came out -0.00114 vs
-0.00105. See `docs/SIMULATOR.md` for the full status and the caveats (bit-repeatability needs strict
deterministic mode; one seed takes a different warm-up path on GPU). The text below is the design-time
document. (The 20-21 Sep proxy was a *different* fork on an older base; it ran 22 runs, ~$35, and was
rejected on the U-net sign flip.)

## Quick start (the intended CLI; the subcommand names are the contract for the code stage)

```bash
# 0. cost and schedule, no AWS calls that write, no GPU. Prints the K60 pinned switch table from the
#    code's own walk, i.e. configs/schedule-K60-TT1793.json (phase 2 at step 336, phase 3 at 829,
#    cooldown at 1214, stop 2361; 492,175,360 tokens, 3.731e17 FLOPs), then the run list,
#    GPU-hours and dollars per instance (--quote-prices skips the read-only aws pricing lookup).
python -m ffsim.gpu.fleet plan --configs ffsim/gpu/configs/gate-k60.json --quote-prices
python -m ffsim.gpu.fleet schedule    # the table alone; `schedule --write` regenerates the JSON from the reference log

# 1. launch ONE g6e.xlarge in us-west-2 (the only subcommand that costs money; it asks first).
#    Owner approval against PROTOCOL.md section 5 is required before this runs.
python -m ffsim.gpu up --region us-west-2 --type g6e.xlarge --key <keypair>

# 2. push the submission train.py, the organizer's prepare.py (read-only copy), the tokenizer,
#    the schedule tables and the run configs; then data setup on the box (once).
python -m ffsim.gpu push --train recipes/K60/train.py

# 3. pre-screen: base s73, K60 (AS-a) s73, relu^2 s73, repeat s73 at the K60 schedule.
#    Measures MFU (re-cost here), the null, the absolute level vs C41 0.95910, and two signs.
python -m ffsim.gpu prescreen --results runs/pre.jsonl

# 4. the gate: the 35-run list of PROTOCOL.md section 3.2 (38 with --marginals), each arm replaying
#    its Trainium run's own schedule from research/sim-data/chipC/<run>/train.log.
python -m ffsim.gpu gate --pairs research/sim-data/validation-pairs.json --results runs/gate.jsonl

# 5. calibrate: pair the GPU rows with the Trainium pairs, both modes (replay vs raw delta;
#    equal-steps vs the k = 0.057 corrected delta), fit the scale factor, measure the noise terms.
python -m ffsim.gpu calibrate --results runs/gate.jsonl --pairs research/sim-data/validation-pairs.json \
    --out research/sim-data/gpu-calibration.json

# 6. verdicts: the seven gates of PROTOCOL.md section 3.3; exit 0 = accepted (scoped by family),
#    1 = rejected (spend nothing more), 2 = incomplete. After acceptance the same command scores
#    candidate runs against the base and prints which ones earn a three-seed Trainium confirmation.
python -m ffsim.gpu verdicts --calibration research/sim-data/gpu-calibration.json --results runs/gate.jsonl
python -m ffsim.gpu verdicts --calibration research/sim-data/gpu-calibration.json --results runs/screen.jsonl

# 7. fetch results, terminate (not stop) the instance.
python -m ffsim.gpu down --fetch runs/ --terminate
```

`plan`, `calibrate` and `verdicts` are pure numpy + stdlib and run on this Windows box without torch;
`up`, `push`, `prescreen`, `gate` and `down` talk to AWS / the instance. Every GPU run is a
`train.py` invocation with the virtual-clock driver in front of it and a results line appended to a
jsonl file (label, arm, seed, schedule table, context signature, val_bpb, tokens and bytes scored,
median step time, MFU).

## What to trust

- A GPU delta is a **sample-efficiency** delta over a pinned Trainium step schedule. It says nothing
  about step time; step counts come from ffsim's step-time model or an S60 screen, never from the GPU.
- Before `verdicts` has returned 0 on the gate, no GPU number influences a chip slot. After it has, a
  verdict is valid only in the families it reproduced (activation form / slope, attention-source
  reuse, optimizer momentum, seed luck), above the printed minimum detectable effect, and it only
  chooses which candidates get the three-seed Trainium confirmation (seeds 73, 58, 67).
- Costs (PROTOCOL.md section 5): one K60-length run is 3.7e17 FLOPs, 1.4-2.0 h on an L40S at 45-30%
  MFU, $2.6-3.8 on g6e.xlarge ($1.861/h, us-west-2 on-demand, 29 Sep); the 4-run pre-screen $11-16; the
  38-run gate $99-144 sequential, or 4.7-6.6 h wall on 16 parallel g6e.xlarge for $113-158. Re-cost
  from the first run's measured step time.
- Phase 1 closes 1 Oct 06:59 UTC; nothing here can affect it. Phase 2 (7 Oct - 5 Nov, 16 chips x 4 h)
  is 256x the chip-seconds, so the K60 calibration carries families, not numbers, and full-scale
  Phase-2 runs are out of reach on a GPU (~364 L40S-hours each); see PROTOCOL.md section 7.
