Data: `research/sim-data/runs.jsonl` (1188 records), `validation-pairs.json` (99 pairs, 73 on the spec's list = `in_task_list`), `official-uploads.csv`. ## 0. Headline

- **Two validation questions, two answers.** Leave-one-pair-out (LOPO: the pair's two runs leave the fit, the same knob values stay in it through other seeds and pairs) measures replicate prediction: on the spec's 73 pairs **sign agreement 85%** (target >= 80%: met), **MAE 0.00038** (target <= 0.0003: NOT met), rmse 0.00054, 97% of observed deltas inside +-2 predicted sd. Leave-one-knob-value-out (LOKVO, section 3e: every fitted run carrying the pair's untried knob value leaves the fit too, so the value is truly unseen) measures what the surrogate is used for, predicting a value that was never run: **sign 84%, MAE 0.00060** (rmse 0.00082, coverage 99%); recipe pairs 81% / 0.00060, decisive recipe pairs 90% / 0.00068. The MAE roughly doubles relative to LOPO. The 80% sign target is met with a margin of 2 pair(s) on the full list (61 of 73 right, 59 needed) and of 0 pair(s) on the recipe pairs (50 of 62 right): inside the sampling noise of a 62-73 pair set (the review's own recomputation, with a slightly different untried-value rule, gave 82% / 79%), so read the LOKVO sign rate as ~80%, not as a pass.
- **Interpolation vs extrapolation** (recipe pairs; the seed / chip pairs move no knob and would count as 'interior'). When the untried value lies between values the refit still holds (LOKVO 'interior', n=10): sign 80%, MAE 0.00021. When it sits outside the remaining range (n=52): sign 81%, MAE 0.00068. Read for search: the surrogate interpolates between values it has seen at ~0.0003-0.0004 and is at ~0.0006-0.0007 MAE / ~80% sign for a value it has never run; `in_support` must be a hard filter for ranking, not a note.
- Recipe pairs only, LOPO (62; the 11 seed / chip pairs test the noise model, not the recipe model): sign 82%, MAE 0.00034; decisive recipe pairs (|observed| >= 0.0003, n=39): sign 95%, MAE 0.00040. In-sample on the same 73 pairs: sign 89%, MAE 0.00022 (meets both targets, but it is not the honest number).

## 1. What was changed in `ffsim/quality.py` to fit this dataset (public API kept)

1. **Missing-knob convention (the decisive fix).** A record's knobs are base.env + overrides (queue) or the config echo (rehearsals). The chip code dirs default to the K57 recipe with every opt-in mechanism off, so a K57-recipe run simply has no `FF_LEAKY_RELU2`; the module as shipped read a missing knob as the K59 default (LK 0.35), which made every LK-vs-K57 control pair a zero knob change. Records are now read with `CODE_DEFAULTS` (LK 0, KEY_OFFSET 0, ACC_IN_GRAPH 0, MTP 0) and, per code version, `code_defaults_for()` (`FF_KEY_OFFSET_RAD` 0.1 for M4-M7: K55/M8 moved the default to 0.3; the M7 `g5` controls never spell it). Candidates passed to `predict()` still read missing knobs as K59 (so `knob_features({})` is all zeros); `predict_record()` uses the record convention. Effect: spec-list LOPO sign 74% -> 85%, MAE 0.00066 -> 0.00038 (attempt A7 vs A3 below).
2. **Lineage.** `code_version` is canonicalised through the dataset's `lineage:` tag (`code_k12off` -> M12, `code_m9` -> M9); the placeholder `code` (the redeployed default dir, 76 evaluated runs from 15-26 Sep) is an unknown era and is dropped.
3. **Era grouping (default).** M9, M10, M10b, M11, M11c, M12, M13, M14 are flag-gated supersets of M9 (the campaign compared M12 arms against M9 controls; 'M12 flags-off is bit-identical to M9'), so they form ONE era `M9+` and the knobs carry every effect. M3-M7 stay separate eras (their base env moved). Configurable: `QualityConfig(era_groups={})` keeps every version apart (attempt A6).
4. **Leakage guard.** After grouping, an era seen in fewer than `min_era_runs` = 2 runs is merged into its parent lineage (nearest older fitted version of the same family), so a single-run treatment can never be absorbed by 'its' era effect. On this dataset that merges {'M8': 'M7'} under the default grouping and {'M10b': 'M10', 'M11c': 'M11', 'M13': 'M12', 'M8': 'M7'} with grouping off (M13 = LK0.5 + the three autograd.Function flags, M11c = torch.maximum leaky form, M10b = abs form, M8 = the K55 rehearsal). Two code-level mechanisms have no knob in the env and are spelled by `LINEAGE_IMPLIED_KNOBS` (M10b -> FF_LEAKY_FORM=abs, M11c -> max) so the merged runs are judged by the `leaky_form_*` features. The two-run era M14 (both runs are the ATTN_SRC treatment, C and D) is covered by the same principle through grouping: it is inside `M9+`, and the `attn_src` feature carries the effect.
5. **Records without effective knobs are not fitted.** Monitor-only / experiments.csv rows (chips A/B `desc:` rows, per-run overrides only, 37 runs) are kept as `holdout` records: the three chip-A pairs of the spec list are evaluated out-of-sample, with the pair file's `knob_changes` / `control_knobs` laid over the monitor rows and their wildcard run names (`A:*_R_g4_s67`) resolved by chip + bpb + seed.
6. **Features.** Added: `attn_src` (M14), `fn_flags` (M13, prior sd 0.001), `mtp_w_tail`, `matrix_lr_log`, `wd_log`, `adamw_lr_log`, `scalar_lr_log`, `ce_bf16`, `ptp_w`, `mom_ramp_log`; `key_offset_rad` replaced by `key_offset_off` + `key_offset_log` (the radius was tried over two decades, 0.03-3.0, and the linear encoding let the 3.0 runs pin the slope at 0.1-0.5); and a quadratic 'bowl' term for every tuned scalar knob (`*_sq`, prior mean +0.0005 per scaled unit^2, sd 0.001: the incumbent sits near an optimum). The data shows the bowl wherever both sides were tried: LK 0 / 0.5, MOM_PEAK 0.93 / 0.97, WD 0.012 / 0.03, MATRIX_LR 1.75 / 2.3 are all worse than the incumbent, which a linear term cannot express.
7. **Reporting.** `support` (knob -> effective values seen, the shape `ffsim.search` reads), `feature_support()` (n runs, values, `identified` = posterior sd narrower than the prior), `unmodelled_knobs()`, `extrapolated_features()`, `steps_slope()`, z-scores / 2-sd coverage / per-family tables in `pair_validation`.
8. **Bowl non-negativity (review F2, `QualityConfig.bowl_nonneg`, default on).** A `*_sq` coefficient that comes out negative is pinned at 0 (prior mean 0, sd 1e-8) and the ridge system re-solved until every bowl is >= 0 (active set, inside the sigma re-estimation loop). A concave bowl means 'the incumbent is a maximum, every move helps', which two single runs of -0.0001 cannot establish; with the curvature gone the knob is carried by its linear term. On this dataset it pins `knob:cooldown_frac_sq`, `knob:wd_log_sq`; `coefficients()` and `feature_support()` flag `pinned` and the prior is reported as specified.
9. **Leave-one-knob-value-out (review Q4, `pair_validation(..., leave_value_out=True)`).** For every feature knob whose effective value differs between the arms, the untried value is the arm's value that is not K59's reference (the treatment's when neither is), and every fitted run carrying any untried value is dropped with the pair before the refit. Rows carry `untried`, `n_value_runs_dropped`, `value_refit`; the report splits interior (untried value inside the refit's range) from extrapolated rows (`n_extrapolated`, `*_interior`, `*_extrapolated`). Section 3e.
10. **Support per value and era (review F2b / Q5).** `support_detail()` = knob -> value -> {n runs, eras}; `value_support(knob, value, code_version)` grades a candidate value `seen` (>= `min_value_runs` = 2 runs, at least one in the candidate's era), `weak` (one run, or runs only from other eras), `interp`, `unseen`, `never`; `feature_support()` flags `era_confounded` features (never two values inside one era) and `design_row` / `predict_delta` note a move on one. `QualityConfig.fit_eras=("M9+",)` restricts the fit to named eras (the rest become holdout arms; attempt A11). `ffsim.search.support_check` (other owner) does not call `value_support`: it counts the fitted runs behind a value itself from the model's rows and applies the same rule (at least the model's `min_value_runs` = 2, one of them in the base's era), grading the rest `weak`, which `report.py` prints as `EXTRAP` and keeps out of the confirmation list (section 12). Locked by `tests/test_ffsim_quality.py`: `test_bowl_constraint_pins_a_concave_bowl`, `test_pair_validation_leave_one_knob_value_out`, `test_support_detail_and_value_support`, `test_era_confounded_features_and_fit_eras`, and the real-data guards in `test_real_dataset_fit_and_anchors` / `test_real_dataset_pair_validation`.

### 3e. Leave-one-knob-value-out: predicting a value that was never run

The 73 spec pairs use only 28 distinct controls (`0626_R_g7_s73` is the control of 12 pairs, `0054_R_g6acc_s58` of 10, `0816_R_g7lk35_s73` of 7), and most treatment values were run at two or three seeds, so leaving one pair out leaves the knob value in the fit: LOPO answers 'can the model reproduce a run it has seen a replicate of'. The search asks a different question, 'what happens at a value nobody has run'. LOKVO answers it: for each pair, every fitted run carrying the pair's untried knob value(s) is dropped as well (an lk35_vs_k57 pair drops all 101 runs with FF_LEAKY_RELU2 = 0, i.e. every K57-recipe and pre-M9 run; an acc_in_graph pair drops the 59 runs with FF_ACC_IN_GRAPH = 0; a seed pair drops nothing extra), the model is refitted and the pair predicted. 51 of the 73 pairs dropped at least one extra run; the untried value stayed inside the refit's range for 21 pairs (interpolation) and fell outside it for 52 (extrapolation).

A mechanism with a different runtime sensitivity needs its own upload before its simulated official score is trusted; its bpb_2m prediction is unaffected. - Verdict: mean +0.00655 vs +0.0066 and sd 0.00045 vs 0.0004: the contract holds, with the caveat that the sd's own 95% interval is 0.00028 .. 0.00111. The wider set has the same mean within its se and a larger sd (0.00065, interval 0.00050 .. 0.00093): the offset drifted by ~0.001 across chips/code since F2, which is why the simulator keeps the chip-C era subset.

## 10. Leakage guard: how single-run code versions were handled

Rule: a code version seen in exactly one fitted run never gets its own era; after canonicalisation and grouping, any era with < 2 runs is merged into the nearest older fitted version of its family (`QualityModel.era_merges`). Under the default grouping the whole M9 family is one era, so M13 (0606_R_g7lks123_s73), M11c (1939_R_g7lrm_s73), M10b (1722_R_g7lrb_s73) and M14 (two ATTN_SRC runs) are inside `M9+` and are judged by `fn_flags`, `leaky_form_max`, `leaky_form_abs` and `attn_src`; M8 (C33_cold_K55, one run) is merged into M7. With grouping off the guard merges {'M10b': 'M10', 'M11c': 'M11', 'M13': 'M12', 'M8': 'M7'}. The test `test_leakage_guard_single_run_era_shares_its_parent` locks the behaviour. Consequence for the M13 pair: with its one run left out, `fn_flags` has no support and the model answers with the prior (predicted -0.00026 for an observed +0.00006, i.e. 'no quality effect', which is the design intent of those flags).

## 12. Caveats

- The spec asks for <= 0.0003 MAE; with single-run pairs whose measurement noise alone gives ~0.0003 expected |error|, the target can only be met in-sample. Use the LOPO numbers (sign 85%, MAE 0.00038; recipe pairs 82% / 0.00034; decisive recipe pairs 95% / 0.00040) as the surrogate's credentials for a value it has seen, and the LOKVO numbers (sign 84%, MAE 0.00060; recipe pairs 81% / 0.00060, of which interior 80% / 0.00021 (n=10) and extrapolated 81% / 0.00068 (n=52)) for a value it has not.
- **The README search, re-run after the fix** (`space-k59-local`, 282 candidates, 1000 draws, rng 0). `ffsim.search.support_check` does not call `value_support`; it counts the fitted runs behind every changed value itself from the model's rows and applies `value_support`'s rule (at least the model's `min_value_runs` = 2, one of them in the base's era), grading the rest `weak`; `report.py` prints `weak` as `EXTRAP` and keeps it out of the 'Next Trainium confirmations' (support levels this run: {'interp': 38, 'interaction': 19, 'weak': 30, 'ok': 3, 'extrap': 191, 'base': 1}; 42 candidates in support). Result: FF_COOLDOWN_FRAC=0.7 / 0.5 predict d vs base -0.00003 / +0.00003 (before the fix -0.00027 .. -0.00017 with P(< base) 0.98-1.00; support now `FF_COOLDOWN_FRAC:weak(n=1, 0 in era M9+)`), 0 of the 48 cooldown candidates are in support and 0 of the 7 confirmations move the cooldown; the best in-support candidate is `FF_LEAKY_RELU2=0.3 FF_WD_SCHED=1` at -0.00007, a rule-2 tie, not a confirmation. Still open in search.py / report.py (other owners): the top-20 table ranks out-of-support rows by predicted mean (6 of the top 12 are cooldown moves flagged EXTRAP; `in_support` should be a hard filter for ranking, not a note), the per-value run count and era appear only in the confirmations' support note, and the coefficient sd behind each confirmation is not printed (`QualityModel.feature_support()[name]['posterior_sd']` / `coefficients()` carry it).
- The rehearsal-vs-queue level (TT 1793 vs 1760) rests on six rehearsal runs; the two K58 rehearsals gained ~0.0005 less over K57 than the queue pairs predicted.
- `sigma` is clamped at its 0.0003 floor: the predictive sds are slightly conservative (97% 2-sd coverage under LOPO, 99% under LOKVO).
- The eras before M9 are fitted for the seed / slope structure they add; the simulator should be asked about M9+ code only (an unseen M15 resolves to `M9+` with an extra 0.0015 sd per generation), and about knobs that varied inside M9+ (section 9a).
